## Architecture

### Plugin System

Moodle is organized around a plugin architecture. Each plugin type has a standard directory:

| Directory | Plugin Type | Purpose |
|-----------|-------------|---------|
| `mod/` | Activity modules | Interactive learning activities (assign, quiz, forum, etc.) |
| `blocks/` | Block plugins | Sidebar widgets for dashboards and courses |
| `local/` | Local plugins | Custom site-specific functionality |
| `theme/` | Themes | Visual presentation and layout |
| `auth/` | Authentication | Login methods (LDAP, OAuth, etc.) |
| `enrol/` | Enrollment | How users join courses |
| `filter/` | Text filters | Content transformations |
| `report/` | Reports | Analytics and reporting |
| `repository/` | Repositories | File source integrations |

Every plugin has a `version.php` defining its version and dependencies, and a `db/` directory for database schema (`install.xml`) and upgrade steps (`upgrade.php`).

### Core Libraries (`lib/`)

- `lib/moodlelib.php` — Core utility functions
- `lib/weblib.php` — HTML output utilities
- `lib/dmllib.php` — Database manipulation (but use `$DB` global, not direct calls)
- `lib/formslib.php` — Form handling (extends `moodleform`)
- `lib/outputlib.php` — Output/renderer system
- `lib/db/` — Core database install/upgrade scripts

### JavaScript Architecture

Moodle uses **AMD modules** (Asynchronous Module Definition) for JavaScript:
- Source files: `<component>/amd/src/*.js`
- Built/minified output: `<component>/amd/build/*.min.js`
- Never edit `build/` files directly — they are generated by Grunt
- Legacy **YUI modules** exist in `<component>/yui/src/` (avoid creating new ones)
- Global `M` object provides Moodle JS API; `Y` is the YUI instance

### CSS/SCSS Architecture

- Theme SCSS: `theme/<name>/scss/` — compiled by Grunt
- Component styles: `<component>/styles.css` — plain CSS
- Boost is the base theme; all custom themes (Adaptable, Moove, etc.) extend it

### Database Access

Always use the global `$DB` object (implements `moodle_database`):
```php
$DB->get_record('table', ['id' => $id]);
$DB->get_records_sql('SELECT ...', $params);
$DB->insert_record('table', $dataobject);
$DB->update_record('table', $dataobject);
```

### Renderer/Output System

Pages use renderers (`core_renderer` or plugin-specific renderers). Output goes through:
```php
$OUTPUT = $PAGE->get_renderer('core');  // or plugin-specific
echo $OUTPUT->header();
echo $OUTPUT->render($widget);
echo $OUTPUT->footer();
```

## Configuration

- Copy `config-dist.php` to `config.php` and fill in database credentials, `$CFG->wwwroot`, and `$CFG->dataroot`
- The production database uses table prefix `r6ua_` (non-standard; default is `mdl_`)
- Production database name: `u774156482_epearl`

## Moodle Development Conventions

- Every PHP file starts with the Moodle copyright boilerplate and `defined('MOODLE_INTERNAL') || die();`
- String localization: all user-facing text goes through `get_string('identifier', 'component')` with corresponding entries in `lang/en/*.php`
- Capabilities are defined in `db/access.php` and checked with `has_capability()` / `require_capability()`
- Navigation and settings are registered in `lib.php` or `settings.php` within each plugin
- Database schema changes require a new migration in `db/upgrade.php` with a version bump in `version.php`
- Test files follow `*_test.php` naming in `tests/` directories; fixtures go in `tests/fixtures/`

### Creating a New Page in a Local Plugin

Standard pattern for any new page:
```php
<?php
require_once('../../config.php');
require_login();
$context = context_system::instance();
require_capability('local/pluginname:view', $context);

$PAGE->set_url(new moodle_url('/local/pluginname/newpage.php'));
$PAGE->set_context($context);
$PAGE->set_title(get_string('pagetitle', 'local_pluginname'));
$PAGE->set_heading(get_string('pageheading', 'local_pluginname'));

echo $OUTPUT->header();
// ... page content or template rendering ...
echo $OUTPUT->footer();
```

### Adding a New Capability

In `db/access.php`:
```php
$capabilities = [
    'local/pluginname:newcap' => [
        'riskbitmask' => RISK_SPAM,
        'captype' => 'write',
        'contextlevel' => CONTEXT_COURSE, // or CONTEXT_SYSTEM
        'archetypes' => [
            'manager' => CAP_ALLOW,
            'editingteacher' => CAP_ALLOW,
        ],
    ],
];
```

Then bump `version.php` and run `php admin/cli/upgrade.php`.

#### Alpha Theme — Custom Sidebar Navigation

**CRITICAL:** The `alpha` theme (active on production) does **NOT** use Moodle's standard `flatnavigation` system. Setting `$node->showinflatnavigation = true` in a plugin's `lib.php` has **NO effect** on the Alpha sidebar.

All sidebar links are hardcoded in `theme/alpha/classes/output/core_renderer.php` via the `mainsidebarmenu()` method. To add a new sidebar link:

1. **For admins:** Add HTML inside the `is_siteadmin($USER)` block
2. **For tutors:** Add a separate role-check block (query `role_assignments` for `teacher` role)

Each sidebar item follows this HTML pattern:
```html
<li class="rui-sidebar-nav-item">
    <a href="{URL}" id="item{Name}" class="rui-sidebar-nav-item-link">
        <span class="rui-sidebar-nav-icon"><i class="fa-solid fa-{icon}"></i></span>
        <span class="rui-sidebar-nav-text">{Label}</span>
    </a>
</li>
```

Plugin `lib.php` navigation hooks still exist for compatibility with other themes but are non-functional with Alpha.

#### Marking History Query Pattern (view.php)

```sql
-- Main query: Get all graded assignments with optional filters
SELECT ag.* FROM {assign_grades} ag
JOIN {assign} a ON a.id = ag.assignment
JOIN {course} c ON c.id = a.course
WHERE ag.grader IS NOT NULL AND ag.grader != -1 AND ag.grader > 2
  [AND userid = ?] [AND c.id = ?] [AND ag.grader = ?]
  [AND ag.timemodified >= ?] [AND ag.timemodified <= ?]
GROUP BY userid, assignment ORDER BY ag.timemodified ASC
```

### `local/assignrelative` — Relative Assignment Deadlines

Automatically adjusts assignment deadlines relative to each student's enrollment date. Lightweight event-driven plugin with no UI.

**Version:** 2025090900 | **No custom capabilities** | **No database tables**

#### How It Works

```
Student views assignment → event fires → observer calculates dates → updates {assign} table
```

1. Observes `\mod_assign\event\course_module_viewed` (priority 9999)
2. Looks up user's earliest enrollment date in the course (`user_enrolments.timestart`)
3. Calculates:
   - Open date: enrollment + 1 day
   - Due date: enrollment + 15 days
   - Cutoff date: enrollment + 20 days
4. Updates the `{assign}` record directly

#### File Structure

```
local/assignrelative/
├── version.php
├── classes/observer.php    # Core logic: adjust_dates($event)
├── db/events.php           # Registers course_module_viewed observer
└── lang/en/local_assignrelative.php
```

#### Critical Design Note

The observer updates the **global** assignment record (not per-user overrides), which means every student view overwrites the dates for all students. For proper per-user deadlines, use Moodle's `assign_overrides` table instead.

#### Extending

- To make offsets configurable: add `settings.php` with admin settings, read via `get_config('local_assignrelative', 'offset_due')`
- To fix the global update issue: write to `{assign_overrides}` with per-user records instead of updating `{assign}`

### `local/sitebackup` — Automated Site Backup Manager

Full-site backup system with local download and Google Drive upload. Backs up database (all courses, grades, enrollments), themes, local plugins, config.php, and optionally moodledata/filedir.

**Version:** 2026020201 (2.1.0) | **Capability:** `local/sitebackup:manage` (manager only, RISK_CONFIG | RISK_DATALOSS)

#### Architecture (v2.0+)

```
User clicks "Local Backup" or "Backup + Drive"
  → view.php creates log record (status=queued)
  → Queues ad-hoc task (task\run_backup)
  → Fire-and-forget cron trigger
  → Redirects to progress.php (live polling UI)

Ad-hoc task (runs via cron, background):
  → backup_manager->run() with progress tracking
  → dump_database() (mysqldump or PHP fallback with multi-row INSERTs)
  → zip_themes() (custom themes only)
  → zip_plugins() (all local/ plugins)
  → copy_config() (config.php)
  → [optional] zip_moodledata() (filedir/)
  → create_master_zip() with manifest.json
  → Move ZIP to $CFG->dataroot/sitebackup/
  → [optional] Upload to Google Drive
  → Update log record (status=success)
```

**Critical: MySQL keepalive** — Hostinger shared hosting has short `wait_timeout`. The `db_keepalive()` method sends `SELECT 1` between every step to prevent "MySQL server has gone away" during long file operations.

**Background execution** — Backups run as ad-hoc tasks via Moodle cron, not in the HTTP request. This prevents browser timeouts and PHP execution limits. Progress is tracked via `progress_step` column polled by `progress.php` every 3 seconds.

- **Live progress page**: Animated spinner, step labels, elapsed timer, progress bar (polls every 3 seconds)
- **Stale detection**: Backups stuck "In Progress" or "Queued" > 2 hours auto-marked as failed
- **Local download**: Green download button per log entry when ZIP exists on disk
- **Diagnose page**: Tests outbound POST to Google's token endpoint using all 3 HTTP methods (Moodle curl, raw cURL, file_get_contents) to identify WAF/firewall issues

#### Google Drive Integration

**OAuth flow:** `get_auth_url()` → Google consent → callback to `authorize.php` → `exchange_code()` → stores tokens in `config_plugins` table.

**Token management:** `token_request()` sends POST to `https://oauth2.googleapis.com/token` using Moodle's `\curl` class (preferred), with fallbacks to raw cURL and `file_get_contents`. Includes debug logging via `log_debug()` (visible in cron output and Moodle debug log).

**Folder management:** `get_or_create_folder()` auto-creates a Drive folder named from the `drive_folder_name` setting (default: "Moodle-Backups"). Folder ID is cached in `google_drive_folder_id` config. Verified on each use (checks if folder still exists and isn't trashed).

**Upload:** Files < 5MB use multipart upload; larger files use resumable chunked upload (5MB chunks). Resumable upload uses raw cURL for chunk management.

**Retention:** `apply_retention()` deletes oldest files beyond `retention_count` after each upload.

**Known issue:** Hostinger WAF may strip POST bodies to `oauth2.googleapis.com/token`. The fix in v2.1.0 uses Moodle's `\curl` class which may route differently. Use `diagnose.php` to test which methods work on your hosting. If all methods fail, contact hosting provider to whitelist outbound POST to `oauth2.googleapis.com`.

**Query 2 — Per-assignment detail per learner per course:**
```sql
SELECT CONCAT(u.id, '-', a.id) AS rowkey, u.id AS userid, ...
       CASE WHEN gg.finalgrade IS NOT NULL AND ... = 'Pass' THEN 'Pass'
            WHEN gg.finalgrade IS NOT NULL AND gg.finalgrade > 0 THEN 'Refer'
            WHEN sub.status = 'submitted' THEN 'Pending Grading'
            WHEN sub.status = 'draft' THEN 'Submitted'
            ELSE 'Not Submitted' END AS grade_status
FROM {user} u
JOIN {user_enrolments} ue ... JOIN {enrol} en ... JOIN {course} c ...
JOIN {assign} a ... JOIN {course_modules} cm (visible=1)
LEFT JOIN {assign_submission} sub (latest=1)
LEFT JOIN {grade_items} gi ... LEFT JOIN {grade_grades} gg ... LEFT JOIN {scale} sc
WHERE u.id IN (...) AND assignment exclusions (IAG, ID Proof, Case Studies)
```

**Query 3 — Tutor lookup (manager only):** Maps each learner to their tutor via group membership.

**Query 4 — Learning hours (v1.1.0):** Streams `{logstore_standard_log}` for all learner+course combos in current year, ordered by `userid, courseid, timecreated ASC`. Processed in PHP with 30-min idle cap into per-user-per-course session arrays.

- **Activity status:** Active (accessed < 30 days), Inactive (30+ days), Created (never logged in)
- Per-course assignments are sorted numerically (Unit 2 before Unit 10) using `preg_match` + `strnatcasecmp`

## Critical SQL Patterns for Dashboard Grading Queries

All grading/marking queries across `tutordash.php`, `markallocation.php`, `admindash.php`, and `admindashboard/index.php` **must** follow these rules. Failure to follow any of these causes dashboard count mismatches.

### Required JOIN Filters

Every query that counts submissions or grades must include:

```sql
-- 1. Only count latest submission per student/assignment (prevents counting old attempts)
JOIN {assign_submission} sub ON ... AND sub.latest = 1

-- 2. Match grade to the SPECIFIC attempt (not just any grade for that user+assignment)
LEFT JOIN {assign_grades} gr ON gr.assignment = a.id AND gr.userid = ... AND gr.attemptnumber = sub.attemptnumber

-- 3. Filter out hidden course modules
JOIN {modules} mdl_m ON mdl_m.name = 'assign'
JOIN {course_modules} cm ON cm.instance = a.id AND cm.course = a.course AND cm.module = mdl_m.id AND cm.visible = 1

-- 4. Exclude suspended/deleted users
JOIN {user} u ON u.id = ... AND u.suspended = 0 AND u.deleted = 0
```

**IMPORTANT:** Never use `mod` as a table alias — it's a reserved MySQL function name (modulus). Use `mdl_m`, `mod_m`, or `mod_imm` instead.

### Moodle Grade Sentinel Value

When Moodle creates a new submission attempt after "Allow another attempt", it inserts a grade record with `grade = -1.00000` meaning "no grade yet". The ungraded check must be:

```sql
AND (gr.id IS NULL OR gr.grade IS NULL OR gr.grade < 0)
```

**Not** just `(gr.id IS NULL OR gr.grade IS NULL)` — that misses the -1 sentinel.

### Assignment Exclusions

These assignment types must be excluded from all marking/overdue/imminent queries:

```sql
AND a.name NOT LIKE '%IAG%'
AND a.name NOT LIKE '%ID Proof%'
AND a.name NOT LIKE '%Case Stud%'
```

- **IAG** — Initial Assessment/Guidance, not graded by tutors
- **ID Proof** — Identity verification upload, not academic work
- **Case Studies** — Feedback-only, no grading needed

### First Submissions vs Resubmissions

"Awaiting Marking" counts only first-time submissions:
```sql
AND sub.attemptnumber = 0
```

"Resubmissions Awaiting Review" counts re-attempts after referral:
```sql
AND sub.attemptnumber > 0
```

Both require `sub.status = 'submitted'` and `sub.latest = 1`.

### Reference Query — Awaiting Marking (First Submissions)

```sql
SELECT COUNT(DISTINCT sub.id)
FROM {groups_members} gm_t
JOIN {groups} g ON g.id = gm_t.groupid
JOIN {groups_members} gm_s ON gm_s.groupid = g.id AND gm_s.userid <> gm_t.userid
JOIN {role_assignments} ra ON ra.userid = gm_s.userid
JOIN {context} ctx ON ctx.id = ra.contextid AND ctx.contextlevel = 50 AND ctx.instanceid = g.courseid
JOIN {role} r ON r.id = ra.roleid AND r.shortname = 'student'
JOIN {user} u ON u.id = gm_s.userid AND u.suspended = 0 AND u.deleted = 0
JOIN {assign} a ON a.course = g.courseid
JOIN {modules} mdl_m ON mdl_m.name = 'assign'
JOIN {course_modules} cm ON cm.instance = a.id AND cm.course = a.course AND cm.module = mdl_m.id AND cm.visible = 1
JOIN {assign_submission} sub ON sub.assignment = a.id AND sub.userid = gm_s.userid
     AND sub.status = 'submitted' AND sub.latest = 1 AND sub.attemptnumber = 0
LEFT JOIN {assign_grades} gr ON gr.assignment = a.id AND gr.userid = gm_s.userid
     AND gr.attemptnumber = sub.attemptnumber
WHERE gm_t.userid = :tutorid
  AND a.name NOT LIKE '%IAG%'
  AND a.name NOT LIKE '%ID Proof%' AND a.name NOT LIKE '%Case Stud%'
  AND (gr.id IS NULL OR gr.grade IS NULL OR gr.grade < 0)
```

### Table Prefix Portability

- **Moodle `{table}` syntax** (preferred): `{assign_submission}` — auto-prefixed by `$DB` methods
- **Raw SQL with `$CFG->prefix`**: `{$prefix}assign_submission` where `$prefix = $CFG->prefix`
- **Never hardcode** `mdl_` or `r6ua_` — local dev uses `mdl_`, production uses `r6ua_`

### Files Using These Patterns

| File | Queries | Prefix Style |
|------|---------|--------------|
| `local/learner/tutordash.php` | mark_sql, resub_sql, o_sql, m_sql | `$CFG->prefix` |
| `local/learner/markallocation.php` | mark, resub, overdue, imm actions | `$CFG->prefix` |
| `local/learner/admindash.php` | 7 queries (per-tutor + global) | `{table}` syntax |
| `local/admindashboard/index.php` | 7 queries (per-tutor + global) | `{table}` syntax |

## Cross-Plugin Data Model

The custom plugins share this core Moodle data model:

```
Users ──enroll──▶ Courses ──contain──▶ Assignments (mod_assign)
  │                  │                        │
  │                  ▼                        ▼
  │               Groups ◀──members──▶   Submissions + Grades
  │            (tutor-learner              (assign_grades,
  │             groupings)                  assign_submission)
  ▼                                           │
Roles & Contexts                              ▼
(student, teacher,                       Grade Items → Scales
 editingteacher, manager)               (grade_items,   (Pass/Refer)
                                          grade_grades)
```

**Key relationships used by custom plugins:**
- Tutors are identified by `teacher` role in `role_assignments`
- Tutor-learner pairing is via shared `groups_members` within a course
- Marking history comes from `assign_grades` (grader = tutor's user ID)
- Results (Pass/Refer) are stored as scale values in `grade_grades.finalgrade` referencing `scale` table
- Extended learner data lives in `local_users` table, keyed by `userid`
- Assignment deadlines can be per-user via `assign_overrides` or global in `assign`
